WEBSITE OPERATIONS / HANDBOOK

網站管理與維運手冊

不知道設定要去哪裡改時，先在這裡找。依目前 L1nG 的網站架構整理：每個項目都有操作位置、步驟和可直接開啟的官方入口。

本頁是操作說明，不會讀取或改動 Cloudflare、Google 帳號設定；顯示的是程式配置，不代表線上環境的即時狀態。控制台選單名稱可能隨官方介面更新。

Cloudflare 控制台 ↗ Zero Trust ↗ Google Analytics ↗ Google Cloud ↗ GitHub 專案 ↗

目前網站與負責服務

五個子網域共用 by-l1ng.com，網頁部署由各自的 Cloudflare Pages 專案承接；主網域不等於首頁。

網站正式網址主要用途

按要做的事情查找

01　新增或更換子網域Pages 自訂網域、DNS、舊網址 301 轉址，以及程式設定

什麼時候看這裡？例如決定將 genealogy-tool.by-l1ng.com 改為 family-tree.by-l1ng.com，或為新作品開設另一個子網域。

  1. 先新增新網址，不要先刪舊網址。至 Cloudflare → Workers & Pages → 找到對應網站的 Pages 專案 → Custom domains → Set up a domain，新增新子網域。族譜網頁請找現有的族譜工具 Pages 專案，不是 l1ng-home。
  2. 檢查 DNS。到 Cloudflare → by-l1ng.com → DNS → Records，確認新子網域已正確連到 Pages 且憑證生效。新增 Pages 網域應從 Pages 的 Custom domains 流程開始，不能只手動建立 CNAME 就當成完成。
  3. 同步網站原始碼。檢查首頁與導覽連結，並更新 L1nG/analytics.js 的站點對照、cookie-consent.js 的允許站點，以及 ga4-api.js 的 GA4 網域篩選。站點間的連結也要一起檢查。
  4. 如果新網址會使用問題反饋，還要同步 Worker。確認 ALLOWED_ORIGINS、TURNSTILE_HOSTNAMES、Worker 來源檢查、Turnstile Widget 的 Hostname Management，以及需要時的 GA4 資料串流設定。修改 GitHub 不代表 Worker 已自動部署。
  5. 正式站與 API 驗收完成後才開 301 轉址。到 Cloudflare → by-l1ng.com → Rules → Redirect Rules，建立只針對舊子網域的永久轉址，保留原路徑及查詢參數。不要設定整個 *.by-l1ng.com，否則會連其他站都轉走。
  6. 最後測試。以一般與無痕瀏覽器分別檢查新舊網址、首頁導覽、Cookie、GA4、問題反饋、手機版、下載功能；確認正常後再考慮清理過期的設定。

提醒：子網域改名涉及多個系統，這個頁面只是教學，不會自動替你做設定變更。301 轉址必須由 Cloudflare 實際建立並驗證。

02　網站沒有更新或部署失敗GitHub 分支、Cloudflare Pages Deployments、正式站與預覽站
  1. 到 GitHub 分支確認修改究竟在 main 還是 genealogy-structural-optimization-20260926；分支預覽不代表正式站已更新。
  2. 到 Cloudflare → Workers & Pages → 對應 Pages 專案 → Deployments，確認 Production 是否使用預期分支、最新部署是否成功及部署時間。l1ng-home 是首頁 Pages 專案。
  3. 部署失敗就開啟該次 Build logs，檢查 Build command、輸出目錄、檔案遺漏、Functions 錯誤；不要只反覆刷新瀏覽器。
  4. 部署成功但內容仍舊時，確認目前開的是正式網域還是 GitHack／pages.dev 預覽，必要時再強制重新整理；沒有部署成功時，清快取通常無法解決。
  5. 留意 l1ng-feedback-api 是獨立 Worker；只更新 Pages 不代表這個 Worker 也更新。
查看 GitHub Actions ↗開啟 Workers & Pages ↗
03　管理中心登入、403 或 Failed to fetchCloudflare Zero Trust、Access 政策、Pages Function 與 Worker Route

到 Zero Trust → Access controls → Applications → L1nG Dashboard。確認只有授權管理員可以通過 Allow 政策，且下列路徑均受保護：

  • home.by-l1ng.com/feedback/admin.html：管理中心頁面，由 Pages Function 驗證。
  • home.by-l1ng.com/feedback/ga4-api：GA4 報表 API，由 Pages Function 驗證。
  • home.by-l1ng.com/feedback/admin-api/*：回饋管理 API，經 Cloudflare Worker Route 交給 l1ng-feedback-api 驗證。
  1. 跳出登入頁／403：先確認 Access 工作階段與 Allow 規則，再核對設定中的 ACCESS_TEAM_DOMAIN、ACCESS_AUD、ADMIN_EMAIL 是否與實際 Access 應用程式一致。
  2. Failed to fetch：先區分是回饋 API 還是 GA4 API；再到瀏覽器開發者工具 → Network 看請求網址、HTTP 狀態與重新導向。網路中斷、Access 驗證與 Worker 路由問題要分開查，不能只憑錯誤文字判定。
  3. 匿名安全驗收：全新無痕視窗請求 /feedback/admin-api/feedback 應被要求登入或拒絕；絕不能直接看到包含玩家資料的 JSON。

不要將整個 /feedback/* 設為管理員專用，否則可能阻擋玩家的公開回饋 API。不要為了排除錯誤而停用 JWT 驗證。

04　GA4 沒資料、流量異常或 API 失敗Google Analytics、Google Cloud 與 Pages 環境變數
  1. 到 Google Analytics，選取 L1nG 的 GA4 資源；在 Admin 中核對 Property details、Data streams、Property access management，確認網站使用的衡量 ID 與服務帳戶讀取權限。
  2. 到 Google Cloud，選取 l1ng-ga4-dashboard 專案，確認 APIs & Services 中 Google Analytics Data API 已啟用，並檢查 IAM & Admin → Service Accounts 的對應帳戶。
  3. 到 Cloudflare → Workers & Pages → l1ng-home → Settings → Variables and Secrets（Production），檢查 GA4_PROPERTY_ID、GA4_SERVICE_ACCOUNT_JSON、ACCESS_TEAM_DOMAIN、ACCESS_AUD 的名稱與環境。私鑰必須是 Secret。
  4. 若更換子網域，請同步核對網站的 GA4 追蹤載入、GA4 資料串流網站網址，以及管理 API 中用於篩選站點的 hostname 對照；否則數據可能存在 GA4，卻沒有出現在管理中心。
  5. 先比較 GA4 官方報表與管理中心的同一日期範圍。Cookie 拒絕統計、事件尚未觸發、GA4 處理延遲都可能使數字不同；歷史未追蹤的點擊無法事後補回。

資料流向：網站追蹤 → GA4；管理中心 → /feedback/ga4-api → Google Analytics Data API。Google 服務帳戶私鑰不會放在前端。

開啟 GA4 ↗Analytics Data API ↗Google Cloud 服務帳戶 ↗
05　玩家回饋、附件或安全驗證異常Cloudflare Worker、D1、R2、Turnstile 與網域允許清單

這套回饋系統與首頁 Pages 的 GA4 Function 是不同服務：l1ng-feedback-api 處理玩家回饋與管理操作；l1ng-feedback-db（D1）保存紀錄；l1ng-feedback-attachments（R2）存放私人附件。

  1. 到 Cloudflare → Workers & Pages → l1ng-feedback-api，查看 Deployments／Logs、Settings → Variables and Secrets，確認 TURNSTILE_SECRET_KEY、ACCESS_TEAM_DOMAIN、ACCESS_AUD、ADMIN_EMAIL 等設定存在且環境正確。
  2. 到 Worker → Settings → Domains & Routes，核對管理 API Route 是否匹配 home.by-l1ng.com/feedback/admin-api/*；不要把整個首頁路由交給回饋 Worker。
  3. 到 Cloudflare → D1 → l1ng-feedback-db 查看資料庫狀況；R2 → l1ng-feedback-attachments 確認附件儲存空間與 Worker 綁定。R2 必須保持私有，不要開 Public Access。
  4. 到 Cloudflare → Turnstile → 現有 Widget → Settings → Hostname Management，檢查 RealDate 與族譜工具使用的主機名稱；新增或改名網址時，同時核對 Worker 的 ALLOWED_ORIGINS、TURNSTILE_HOSTNAMES。
  5. 以不含私人資料的測試回饋確認提交、憑證查詢、管理員讀取、附件上傳及回覆。遇到失敗，應查看 Worker Logs 與回應狀態，勿直接清空 D1 或 R2。

D1 / R2 不是可以重建就自動恢復玩家資料的快取。操作刪除、重建資料表或更換 Bucket 前，應先有安全備份及回復方案。

Cloudflare Worker / D1 / R2 ↗Turnstile 管理教學 ↗Worker Route 官方教學 ↗
06　Cookie、隱私與跨站統計五個子網域共用 Cookie，訪客的統計同意與拒絕
  1. 共用 Cookie 的 Domain 是 .by-l1ng.com；不要因為只改一個子網域，就把共用 Cookie Domain 改成單一網站。
  2. 可在 L1nG/cookie-consent.js 檢查已允許的網站名稱及統計載入政策；更換網域時同步新增或移除已授權的主機名稱。
  3. 在無痕視窗重新檢查接受統計、拒絕統計、開啟偏好設定三種操作，以及子網域間選擇是否一致。不得為了讓 GA4 數字增加而繞過訪客的同意設定。
查看 Cookie 程式 ↗比對 GA4 報表 ↗

症狀先檢查哪裡

新網域打不開、404 / 522Pages Custom domains → DNS Records → 網域憑證與 Redirect Rules

每次修改前

確認正在編輯正確的分支與專案、記錄原設定、確認備份是否存在、核對變更範圍；修改身分驗證、DNS、Worker Route 或資料庫時，先規劃回復方法。

每次修改後

查看部署是否成功，使用電腦與手機、登入與無痕視窗測試；至少驗證站內連結、Cookie、GA4、管理 API、安全登入及問題反饋，再宣布正式完成。

安全原則：GA4_SERVICE_ACCOUNT_JSON、TURNSTILE_SECRET_KEY、Access JWT 與私人憑證都不能貼在 GitHub、聊天室、公開 HTML 或玩家回饋裡。這份手冊只列變數名稱，不儲存任何密鑰。

手冊內容以 2026/10/18 的專案程式架構為基礎；新增站點、調整部署或改動安全配置後，也應同步更新此頁，避免教學過期。

先選擇開始日期，再選擇結束日期。
